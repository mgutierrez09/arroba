01 / Product decision

Ship a customer-owned deployment product, not a larger sidebar.

Recommended thesis Chariox should become the managed host for provider-native agent apps. A builder publishes an immutable release; a customer claims a deployment into their organization, connects their own provider and integration credentials, controls who may use it, and operates it on a Chariox-managed URL or their own domain.

The differentiated product is a claimable agent app release. It is narrower and more defensible than trying to match every n8n workflow-building feature. Chariox can own the deployment, handoff, runtime, authentication, credential binding, and operational experience for developers and agencies that do not want custom infrastructure.

01

Immutable releases

Production changes move through explicit release promotion and rollback. Deployment controls cannot silently rewrite workflow semantics.

02

Customer ownership

The destination organization owns access, credentials, domains, billing, and production activation. Builder access is optional and revocable.

03

Runtime-held credentials

Provider credential bytes never enter publication packages or ordinary Cloud deployment records. Login uses provider-native harnesses in the runtime plane.

04

One shared authority

The kernel remains workflow and execution authority. Cloud is control plane; relay and ingress remain scoped transport and policy boundaries.

Initial product focus

  • Agencies and independent developers delivering an agent portal or agent API to a company.
  • Teams that want provider-native Codex, Claude, or OpenCode execution without operating application infrastructure.
  • Two deployment kinds on one foundation: browser-facing Agent App and programmatic Endpoint.
  • Managed hosted runtime as the default handoff; local runtime and export/self-host remain supported sovereignty options.

Explicit non-goals for the first release

  • Cloning n8n's full integration catalog, embedded editor, or generic no-code automation breadth.
  • Arbitrary customer frontend code, Kubernetes, marketplace economics, or multi-cloud orchestration.
  • Automatic unreviewed production updates from the builder's mutable workflow.
  • Using persistent workflow patches as a general-purpose customer database.

05 / Release contract

Package v3 is the immutable managed-hosting admission unit.

OSS now exports deployment-contract.json in every package v3 archive. The contract identifies the source, content digest and digest scope; declares routes, provider and credential requirements, resources, capabilities, presentation, network ceilings and runtime compatibility; and is validated in both repositories. Package v1/v2 readers remain explicit legacy adapters for local compatibility and must not be treated as equivalent managed-hosting releases.

Required contract sections

  • Identity: stable release/package IDs, digest, source provenance, creator, timestamps, minimum runtime and protocol versions.
  • Routes: path, transport, methods, input/output schema, required roles, session behavior, streaming, timeout, idempotency hints.
  • Provider requirements: provider, model constraints, allowed substitutions, capability needs, readiness test.
  • Credential slots: stable slot ID, kind, label, provider/integration, required/optional, scope, allowed hosts, uses, test method.
  • Typed configuration: stable key, scalar/enum/schema type, default, constraints, sensitivity flag, environment scope.
  • Capabilities: maximum actions, manipulation permissions, extension requirements, scripts, MCPs, skills, connectors, filesystem and network policy.
  • Resources: expected concurrency, memory class, replicas, storage, schedules, egress destinations, region/data sensitivity hints.
  • Presentation: app kind, assets manifest, immutable content hashes, entry route, display name and icon metadata.

Compatibility rules

  • A deployment may tighten route roles, network access, provider choice, replicas, limits, schedules, and capabilities; it may never broaden the release's declared maximum.
  • Workflow graph, prompts, endpoint routes, required roles, actions, assets, or capability maxima require a new immutable release.
  • Access policies, credential bindings, typed non-secret settings, domain, allowed runtime override, region, size, replicas, budgets and alerts are environment configuration.
  • Any serialized OSS protocol shape change follows the repository protocol rule: bump the shared version, update snapshot/hash tests, update dependent minimum versions, and add a focused drill.

Implemented admission path

  • Archive extraction is bounded and structured; Cloud verifies archive size, file safety, package digest, contract schema, contract/package identity and immutable release metadata before promotion.
  • The v3 compatibility block carries the minimum local daemon protocol. Runners advertise the probed protocol of an immutable Docker image ID, and incompatible jobs are not claimable or recoverable on that image.
  • The publication image pins and build-verifies Codex CLI 0.144.0, OpenCode 1.18.23 and Claude Code 2.1.212. The contract maps provider slots to stable official bundle IDs so an environment can tighten, never substitute or broaden, the declared provider ceiling.
  • Hosted activation requires package v3, an enforced network policy snapshot and supported provider bundle references. The Cloud egress-policy compiler, lifecycle admission, aligned API-to-worker policy snapshot, runner orchestration, recovery and cleanup are committed and pass local and designated-Hetzner fail-closed acceptance.
Design constraint The package must describe what a customer needs to provide without containing what the builder provided. A credential slot says "GitHub installation with repository read scope"; it never contains a GitHub token or builder account reference.

06 / Security foundation

Keep the landed containment controls below every client.

Phase 0 control-plane containment is implemented: authenticated identity and membership are service-derived, browser mutations are CSRF checked, cross-account object access is denied, canonical routing is deployment-scoped and managed persistent patches are rejected. Later work added signed caller claims, credential and process isolation, immutable runtime compatibility, resource ceilings and an audit bridge. These controls remain implementation baselines, not proof that the final hosted product matrix has passed.

The normative actor, asset, trust-boundary, abuse-case, residual-risk and verification baseline is maintained in Deployed Workflows Threat Model.

Control-plane requirements

  • Derive actor and account membership from the authenticated browser/API session; do not trust body/query identity fields.
  • Apply CSRF protection to browser mutations and explicit bearer/scoped credentials to machine APIs.
  • Define control roles: owner, admin, deployer, operator, viewer, billing. Enforce them in repository/service policy, not only React.
  • Verify WorkOS assertions only at the Cloud identity boundary, map them to a Chariox principal, and authorize from local account/deployment membership. Never treat an IdP role or organization claim as sufficient authority by itself.
  • Scope every lookup and mutation by destination account and deployment ID. Add cross-account denial tests.
  • Hash claim and API-key tokens at rest, display secrets once, support expiry and revocation, and log security events without token content.
  • Move destructive or sensitive operations through auditable service methods with idempotency keys.

Public ingress requirements

  • Resolve a globally unique verified host to one deployment/environment; never select the latest matching slug.
  • Authenticate before HTTP, SSE, WebSocket, and MCP upgrade/stream creation.
  • Strip caller-supplied identity and internal Chariox headers, then inject a short-lived signed invocation envelope.
  • Include deployment_id, environment_id, sub, org, roles, aud, expiry, nonce, and invocation ID in trusted claims.
  • Verify claims again at the runtime boundary and enforce the package route's required_role.
  • Keep identity structured. Do not automatically splice identity claims into model-visible prompt text.
  • Apply per-deployment and per-caller request, concurrency, queue, body-size, duration and spending limits.
  • Validate CORS, CSRF, cookie scope, WebSocket Origin, forwarded headers, redirect and content-security policy behavior.

Hosted egress requirements

  • Create one Docker network per deployment revision with --internal; attach the publication container only to that network.
  • Run one dedicated unprivileged CONNECT gateway per revision, dual-homed on the internal revision network and a separate egress-capable network. Do not place the publication container on the egress network.
  • Compile a digest-bound policy only from the immutable v3 ceiling and environment tightening. Permit exact canonical lowercase DNS names on TLS port 443 only.
  • Reject the request unless every A and AAAA answer is public unicast, pin the chosen validated address for the upstream connection, and require TLS ClientHello SNI to equal the CONNECT host exactly.
  • Provide no direct route and no fallback when the gateway, DNS, policy or provider bundle is missing or unhealthy. Hosted start, restart, recovery and promotion must reject packages without an enforced deny-by-default policy.
Persistent patch policy Keep persistent workflow patching unavailable for customer deployments until strong authentication, authorization, reviewable diffs, audit, rollback, expiry, concurrency handling, and capability limits are implemented. A deployment may not become a hidden workflow editor.

06A / Identity platform

Use WorkOS to authenticate people; keep Chariox authoritative for access.

WorkOS AuthKit is the selected human-identity platform for the Cloud control plane, future React Native clients, and the default interactive identity option for deployed Agent Apps. This replaces the Auth0-specific integration and the current development shortcut. It does not move account ownership, deployment roles, audience policy, runtime sessions, relay tokens, provider credentials, or billing authority out of Chariox.

Selected architecture

WorkOS proves who the person is and supplies organization, SSO, and directory lifecycle context. Chariox maps that verified subject to its own User, maps a WorkOS organization to its own Account, and evaluates every control-plane and deployment authorization from local membership and policy. Cloud then mints narrowly scoped Chariox sessions and invocation claims. WorkOS tokens never enter the kernel, relay, hosted workflow container, provider CLI, or publication package.

07 / Customer handoff

A claim flow should replace credential and ownership copying.

  1. Create release. Builder publishes an immutable release and selects "Deploy for customer." Chariox validates the package contract before issuing an invitation.
  2. Review invitation. Customer sees the app identity, builder, required providers and integrations, capabilities, data/egress implications, runtime mode, estimated cost and offered builder role.
  3. Claim ownership. Customer authenticates through WorkOS, chooses or creates the explicitly mapped Chariox account, accepts terms, selects billing ownership, and creates the deployment project. The local claim remains single-use, expiring, destination-bound, and idempotent.
  4. Connect dependencies. Customer supplies typed configuration, provider credentials and integration credentials. Builder secrets are never transferred.
  5. Set audience. Customer selects WorkOS-backed invitation/organization/SSO, public, explicit allowlist, generic OIDC/JWT, or machine access and maps identities to published route roles.
  6. Choose address. Chariox assigns a stable default hostname. Customer may attach and verify a custom domain.
  7. Private preview. Chariox runs contract checks and a smoke invocation in preview. Activation stays blocked until all required checks are green.
  8. Activate. Customer promotes the verified release/configuration snapshot to production.
  9. Maintain. Builder proposes future releases. Customer reviews the release and config diff, then promotes or declines it. Rollback is always available.
  10. Revoke cleanly. Customer may remove builder access without breaking runtime ownership, credentials, domain, history, or production availability.

Ownership modes

Customer-owned

Default. Customer owns deployment, billing, credentials and activation. Builder may receive a revocable maintainer role.

Builder-managed

Agency remains operator and billing owner while customer controls audience membership. Ownership transfer remains available later.

Export / self-host

Customer receives the immutable package and declared requirements, then operates it outside managed hosting.

Internal team

No handoff. Source and deployment stay within one organization, but release, credentials and audience boundaries remain identical.

12 / Runtime operations

Production hosting needs more than start, stop, and logs.

Release and configuration operations

  • Build once, verify digest/signature, promote the same immutable release across environments.
  • Snapshot environment configuration and credential binding versions with every promotion.
  • Use readiness gates and rolling activation; switch ingress only after the replacement is healthy.
  • Rollback release and configuration pointer atomically. State/database rollback is a separate explicit operation.
  • Keep prior runtime for a short bounded drain window, then clean it and preserve diagnostic metadata.

Resource, usage, and abuse controls

  • Per environment: replicas, max concurrency, queue depth/age, request body, timeout, runtime memory/CPU class, storage and egress policy.
  • Per caller: request rate, active sessions, token/cost estimate and daily/monthly budget.
  • Customer alerts: credentials expiring, health degraded, error/latency threshold, queue saturation, budget percentage and domain/TLS issue.
  • Emergency controls: deny new invocations, stop environment, revoke one audience key, unbind one credential, or disable one route without deleting history.

Hosted ceilings, supervision, and cleanup

  • The runner validates every limit before Docker. Current defaults are 2 GiB memory with swap disabled, 2 CPUs, 256 PIDs and 4,096 open files; accepted configurable ranges remain bounded and malformed or unknown fields fail before launch.
  • Hosted containers use a read-only root, no-new-privileges, a reduced capability set, bounded tmpfs mounts and separate kernel, provider, gateway and action identities/homes. The platform runner key never enters the runtime container.
  • tini owns PID 1. The standalone entrypoint supervises kernel, publication gateway and optional action server; an unexpected child exit terminates siblings, waits for them and exits nonzero so the runner can reconcile instead of serving a partial runtime.
  • Promotion keeps the prior healthy revision through candidate readiness and a bounded drain, then removes superseded containers and capabilities. Stop, delete, failed start, runner restart and credential rotation/revocation must converge without an orphaned container, profile or route.
